# 开发规范

本规范用于 NPuzzle.resolution 小组协作。项目环境、启动参数和运行命令见 [项目 README](../README.md)，原始框架调整见 [框架修改说明](SOURCE_CHANGES.md)。文中的源码路径均相对仓库根目录。

## 1. 开发环境与文件格式

- 使用 JDK 21，IDEA 打开包含 `WattAi/` 的仓库根目录，将 `WattAi/src` 设为 Sources Root。
- Java 源码及新建文本文件统一使用 UTF-8（无 BOM）、LF 换行，并保留文件末尾换行，遵循根目录 `.editorconfig` 和 `.gitattributes`。
- 新增或修改 Java 代码采用 4 个空格缩进；类名使用 `UpperCamelCase`，方法和变量使用 `lowerCamelCase`，常量使用 `UPPER_SNAKE_CASE`。
- 保留既有包名和目录结构；包声明必须与 `WattAi/src` 下的路径一致。
- 只格式化本次修改涉及的代码，避免整库格式化造成无关差异。
- 注释说明约束、算法思路和容易误解的边界；公开方法的参数、返回值和异常约定发生变化时，同步更新说明。

## 2. 模块分工与接口约定

| 目录 | 主要职责 |
| --- | --- |
| `WattAi/src/stud/g01/problem/npuzzle/` | 棋盘状态、合法移动、目标判断、启发函数 |
| `WattAi/src/stud/g01/runner/` | 读取测试输入，创建问题、队列和求解器 |
| `WattAi/src/stud/g01/queue/` | 搜索边界队列、状态去重和结点更新 |
| `WattAi/src/stud/g01/solver/` | IDA* 求解流程 |
| `WattAi/src/core/` | 框架接口、通用搜索流程和程序入口 |

实验实现优先放在 `stud/g01/`。需要修改 `core/` 的接口、共享运行参数或引入依赖时，先与相关模块负责人约定影响范围，并在 Pull Request 中说明兼容方式。第三方工具类保留原版权和许可证声明。

多人同时开发前，约定棋盘编码、空格表示、目标状态、动作方向、移动代价，以及无解时的返回方式。实现遵循以下规则：

- `equals` 与 `hashCode` 使用相同的棋盘状态定义；不同对象表示同一棋盘时，应能正确去重。
- 棋盘进入哈希集合或队列后，不修改参与相等判断和哈希计算的数据。生成后继状态时避免意外修改父状态。
- 需要保证最优解时，启发函数不得高估实际剩余代价；目标状态的启发值为 `0`。曼哈顿距离和错位数按约定的目标位置计算，并排除空格。
- 队列遵循 `Frontier` 接口；同一状态重复入队时按约定的评价规则保留更优结点，处理好结点更新和堆顺序。
- IDA* 使用 `g + h` 控制阈值，后续阈值依据本轮超过阈值的最小评价值更新；处理路径中的重复状态和无解终止条件。

## 3. 分支与提交

`main` 保持可编译、PathFinding 示例可运行。开发流程如下：

1. 从最新 `main` 创建功能分支，例如 `feat/puzzle-board`、`feat/idastar`、`fix/frontier-update`、`docs/development`。
2. 每次提交围绕一个明确目的，提交前查看 `git diff`，确认没有个人配置、编译产物或其他无关文件。
3. 提交信息采用 `类型: 简要说明`，例如 `feat: 实现曼哈顿距离启发函数`、`fix: 修复队列重复状态更新`、`docs: 补充运行说明`。
4. 推送功能分支并创建 Pull Request，说明改动后的行为、涉及模块和实际验证结果；算法或跨模块改动由至少一位协作者审核后合并。
5. 同步分支或解决冲突后，重新执行受影响的验证。仅在自己的开发分支上改写提交历史，避免覆盖他人的提交。

## 4. 提交前验证

代码改动至少按照 README 中的命令完成 UTF-8 编译并运行 PathFinding 示例；GitHub Actions 当前也执行这两项检查。CI 通过表示编译和寻路示例通过，NPuzzle 算法正确性需要另行验证。

NPuzzle 相关实现还需按改动范围验证：

| 改动范围 | 建议检查 |
| --- | --- |
| 棋盘与动作 | 已达目标、一两步可解、边界空格、合法移动、父状态保持不变、相等和哈希一致 |
| 启发函数 | 目标状态为 `0`、手算简单棋盘、空格不计入距离、与目标布局一致 |
| 队列 | 重复状态、更优结点替换、出队次序、清空后的状态 |
| A* / IDA* 求解 | 简单棋盘的最优步数、解路径每步合法、无解状态、重复状态处理；可行时比较两种算法的解代价 |

优先使用小型、结果明确的用例定位问题，再运行耗时较长的实验。修复逻辑缺陷时，保留能复现该缺陷的用例；新增测试代码放在 `WattAi/tests/`，并附实际执行命令。当前项目没有测试框架，新增测试不得直接假定 JUnit 或 Maven 已可用。

纯文档和文件整理只需检查链接、路径及文件是否完整，无需重复运行算法。

## 5. 测试资料与实验结果

- `WattAi/resources/` 存放程序运行时读取的数据。
- `benchmarks/` 存放已有 A*、IDA* 测试用例、曼哈顿距离测试结果及测试机信息，保留原文件名和内容。
- 新实验结果放入 `benchmarks/runs/<实验名称>/`，避免覆盖已有结果；同时简要记录 Git 提交版本、运行命令、输入文件、算法、启发函数、JDK 和测试机信息，便于复现。
- 比较运行时间或扩展结点数时，使用一致的输入、启发函数和统计口径。
